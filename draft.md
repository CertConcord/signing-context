# Protected Signing Operation Context — draft 02

Status: a focused, opt-in amendment proposal for experimental signing interfaces. It is not a browser API, a registered WebAuthn extension, a CSC conformance claim, or evidence of deployed platform support.

## 1. Existing fields and the remaining gap

The comparison is against the exact sources in [sources.json](sources.json). A verified raw signature proves use of a private key over the algorithm's input; it does not by itself prove why the operation was allowed.

| Interface | Existing key, input and authority fields | Existing result and assurance | Missing for the protected operation considered here |
| --- | --- | --- | --- |
| WebAuthn `sign` proposal | `allowCredentials`, `keyHandleByCredential`, `tbs`, selected credential ID, COSE algorithm, RP ID and the ordinary WebAuthn challenge/origin | The signing-key attestation can convey fixed UP/UV policy; the assertion authenticates authenticator data and its `sign.sig` extension output. The raw signature signs `tbs` unaltered, without client or authenticator data. | No per-operation authorization of a particular `tbs` under an application policy, and no durable lookup by a client-known operation ID after an initial result is lost. The signed assertion and attested UP/UV policy must retain their own narrower meanings. |
| Remote CryptoKeys proposal and Web Crypto `sign` | `getRemoteKey` selects a handle using `userIdentifier` and optionally `keyId`; `CryptoKey` has `usages` and an optional `expiresAt`; `subtle.sign(algorithm, key, data)` supplies the actual message | The browser passes origin to the platform. The explainer leaves platform access control and consent checks out of scope and permits a later full key search when `keyId` is absent. | No authenticated provider selection, protected authorization bound to the exact key and input, or durable same-operation result lookup. A nonextractable handle does not fill those gaps. |
| CSC API 2.2.0.0 `signatures/signHash` | Service endpoint, `credentialID`, SAD or credential-scoped access token, ordered `hashes`, `hashAlgorithmOID`, `signAlgo`/`signAlgoParams`, and `operationMode`; authorization can bind hashes | The service checks authorized hashes. Asynchronous mode returns a server-generated `responseID`; `signatures/signPolling(requestID)` retrieves a previously accepted asynchronous result. `clientData` is application data and can carry a transaction identifier. | Existing polling needs the server-generated ID, which may be lost with the initial response. CSC does not assign idempotent admission and lookup semantics to client-supplied `clientData`. Those semantics require an explicit service profile. |

Source locations: the pinned [WebAuthn `sign` extension](https://raw.githubusercontent.com/w3c/webauthn/28e878d6b31130a3621c0eb793529a65bf3dc162/index.bs) at `#sctn-sign-extension`, the pinned [Remote CryptoKeys explainer](https://raw.githubusercontent.com/WebKit/explainers/6ce73fa4f91bbe7fb1990b6c1e7276c8dbd12609/remote-cryptokeys/README.md) at `RemoteKeyParams` and `getRemoteKey`, and the [CSC API 2.2.0.0](https://cloudsignatureconsortium.org/wp-content/uploads/2025/11/csc-api.pdf) at sections 11.13 and 11.15. [The separately pinned WebAuthn version 5 draft](https://raw.githubusercontent.com/yubicolabs/webauthn-sign-extension/812b911a2a5d737d2ebdb91ead8bfd78f8277710/index.bs) remains a proposal source, not deployment evidence.

The WebAuthn signing proposal already binds a selected signing key handle and exact `tbs` in the ceremony. CSC already defines credential, hash, authorization and asynchronous polling fields. This proposal does not duplicate those fields, change what their signature algorithms sign, or add a generic signed envelope, permit or receipt. Its only proposed CSC wire-level change is a negotiated meaning for existing `clientData` and a client-ID lookup form of existing polling, as specified in section 4. Other hosts may choose a different API shape but must meet the same behavior before claiming it.

## 2. Conditional protected-operation contract

An implementation claims **protected authorization** only if the component controlling key invocation checks the authorization before invoking the key. It must bind the authorization to the actually selected provider or authenticator, key or credential, algorithm including parameters, input kind, exact input bytes or ordered digest bytes, authenticated requester scope, and one operation ID. The requester scope is WebAuthn RP ID and origin for a WebAuthn host, browser origin for a remote-key host, or authenticated service/client audience for CSC; it is not a fictitious universal origin field. An authorization for a digest does not prove that the signer saw or approved the digest's preimage.

The implementation must reject an unavailable selected key, changed algorithm or parameters, changed input, expired or revoked authorization, changed audience, and a same-ID/different-request collision before dispatch. It must not silently select another key or provider. If the host permits multiple eligible credentials, the verifier uses the *actual* selected credential ID and its matching key handle; a mere list of eligible keys is not an authorization for all of them. A logical credential ID or service URL alone is insufficient when it can be remapped: the key-invoking component must resolve and pin an immutable identity for the actual provider instance and key version or key material under that ID. If it cannot distinguish an alias remap, it cannot claim protected authorization for that selection. For prehashed algorithms, the hash algorithm and whether the bytes are a digest are part of the authorization. For message-signing algorithms, the exact message bytes are the input. A transport must preserve those bytes across asynchronous boundaries.

The enforcement component durably reserves the ID and the authorization's usable slot with an immutable comparison of all security-relevant request fields and the resolved provider/key identities before dispatch. At the key-invoking boundary it re-resolves or uses a pinned handle and compares the effective provider instance, key identity, algorithm and input to that reservation again; any mismatch fails without invocation, even if the credential ID or service URL is unchanged. It records dispatch before invoking an external signer. The slot remains spent through crashes, revocation, key-handle reallocation and account recovery. A completed outcome is immutable. An unresolved dispatch must remain unresolved until the original provider's outcome is established; a timeout or cancellation cannot prove non-execution. A same-ID retry or status query never invokes the key to recreate a missing response. If outcome retention ends, a spent-grant or ID tombstone must still prevent reuse for the lifetime of any replayable authorization. If the provider cannot guarantee these properties, it must not claim **same-operation recovery**.

The authenticated outcome must identify, or be verifiably linked to, the resolved provider/key identity as well as the selected credential, algorithm, input and operation ID. Existing WebAuthn assertion data or an authenticated service response may carry that link where the actual signer supplies it; an unsigned field appended by the application is not enforcement evidence. A raw signature alone cannot prove the protected authorization check. The caller must authenticate to query the outcome, and the service must scope query access to the original requester. Retention and expiry must be declared; after retention ends, the answer is unknown, never permission to replay under the old ID.

## 3. Capability declaration and evidence

Capability statements are separate claims, not an ordered ladder:

1. **Raw signing:** the API can sign with a selected key and algorithm.
2. **Ceremony evidence:** an authenticated WebAuthn assertion can show the ceremony's RP binding and UP/UV bits, and verified signing-key attestation can support its fixed policy. This does not assert document display or application-specific authorization.
3. **Protected authorization:** the actual key-invoking component enforces the bound authorization described in section 2.
4. **Same-operation recovery:** that component also implements the durable reservation, immutable result and client-known lookup described in section 2.
5. **Protected display or additional user verification:** claimed only with separate authenticated evidence of the actual displayed content or verification event.

A declaration names the implementation and exact supported scope, including algorithms, input kind, requester scope, retention and recovery behavior. A TLS-authenticated service statement can declare a service policy; it does not independently prove the service's internal enforcement. A stronger hardware or isolated-component claim needs verifiable evidence binding the implementation, admitted policy authority and update or rollback behavior. A caller must reject a stronger unsupported claim, not infer it from nonextractability, a generic `sign` result, an RP-generated receipt or a provider's self-description.

## 4. Minimal CSC profile example

This section is a **proposed opt-in profile**, not CSC 2.2.0.0 behavior. It illustrates the smallest semantic addition in an API that already has the other fields. The provider first declares this exact profile and retention policy through an authenticated service policy. For one `signatures/signHash` request with one hash and asynchronous `operationMode: "A"`, the client chooses a fresh, unpredictable `clientData` value of the form `sc1:` followed by unpadded base64url encoding of 16 random bytes. Under this profile, and only under it, the provider interprets that value as the operation ID. The existing server-generated `responseID` and `signPolling(requestID)` remain valid.

Before signing, the service durably binds that ID and its server-generated `responseID` to the authenticated client/audience, selected service and `credentialID`, internally resolved provider instance and key identity, one authorized digest, `hashAlgorithmOID`, `signAlgo` and parameters, SAD or credential authorization reference, and the requested operation mode. The resolved identities are internal enforcement values, not new CSC request fields. It enforces the authorization against this exact tuple. Repeating `signatures/signHash` with the same ID and tuple returns the original `responseID`; changing any bound field or remapping the same credential to another key rejects without dispatch. The service must not rely on a digest of a JSON serialization whose normalization is unspecified: it compares the decoded typed values and exact digest bytes, including their order where an API supports more than one. The one-hash restriction here avoids defining batch partial-result semantics.

If the initial response is lost, a profile-aware client may call `signatures/signPolling` with `clientData` alone, without `requestID`, to look up its own operation. This is the sole proposed polling extension. It returns the original completed outcome, pending state or an explicit unresolved outcome under the declared retention policy. It must never submit a new signing request. The base CSC method requires `requestID`; a service that supports only that base method cannot claim this profile. A lookup must not reveal another client's operation or treat an unknown or expired ID as proof that the key was not used. `clientData` has no idempotency guarantee outside this negotiated profile and must not be repurposed silently by an ordinary CSC client.

This example does not claim CSC SAD is always bound to one digest or one key. The profile is available only for an authorization mode in which the service can enforce the exact tuple and consume one usable signature slot. A broader SAD, an unscoped key search, a synchronous-only endpoint or a provider without durable reservation yields only the narrower supported capability. The same requirements could inform a future WebAuthn or Remote CryptoKeys amendment; no browser or authenticator behavior is asserted here.

## 5. Privacy, evaluation and open questions

Stable provider, key and operation identifiers can correlate activity. The client ID is random and scoped to one service and requester; outcome queries require authorization, disclosure is limited, and retention is bounded. A status query itself can reveal signing activity, so a profile must define rate limits and observable errors without confusing access denial with proof of non-execution.

[cases.json](cases.json) contains synthetic positive and negative transition vectors. Its fixed `clientData` value is for reproducibility; live clients must generate fresh unpredictable values. `baseSelection` and `baseAuthorizationSelection` model internal provider/key identities, not CSC wire fields. `npm run check` replays the vectors against a one-operation reference model and validates the pinned source metadata. Vector statuses describe model states, not CSC wire responses. The model's `authenticated` flag stands for verification of an outcome bound to the recorded request and resolved selection; it is not a cryptographic proof. The model tests the proposed contract, not a deployed browser, authenticator, CSC server, or hardware enforcement. Open design work remains for an interoperable WebAuthn or remote-key API shape, independently verifiable enforcement evidence, and the error/status encoding of the optional CSC profile.
