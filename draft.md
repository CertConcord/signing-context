# Protected Signing Operation Context — draft 02

Status: a focused, opt-in amendment proposal for experimental signing interfaces. It is not a browser API, a registered WebAuthn extension, a CSC conformance claim, or evidence of deployed platform support.

## 1. Existing fields and the remaining gap

The comparison is against the exact sources in [sources.json](sources.json). A verified raw signature proves use of a private key over the algorithm's input; it does not by itself prove why the operation was allowed.

| Interface | Existing key, input and authority fields | Existing result and assurance | Missing for the protected operation considered here |
| --- | --- | --- | --- |
| WebAuthn `sign` proposal, version 6 | `allowCredentials`, `signByCredential` mapping credential IDs to `keyHandle` and `tbs`, the selected credential ID, COSE algorithm, RP ID and ordinary WebAuthn challenge/origin | The signing-key attestation can convey fixed UP/UV policy; the assertion authenticates authenticator data containing the `previewSign5` extension's integer CBOR member 6 (`sig`), which the client exposes as `previewSign5.signature`. Optional `support: true` requests supported parent-credential and signing-algorithm combinations. The raw signature signs `tbs` unaltered, without client or authenticator data. | No per-operation authorization of a particular `tbs` under an application policy, and no durable lookup by a client-known operation ID after an initial result is lost. Algorithm support discovery, the signed assertion and attested UP/UV policy each retain their narrower meanings. |
| Remote CryptoKeys proposal and Web Crypto `sign` | `getRemoteKey` selects a handle using `userIdentifier` and optionally `keyId`; `CryptoKey` has `usages` and an optional `expiresAt`; `subtle.sign(algorithm, key, data)` supplies the actual message | The browser passes origin to the platform. The explainer leaves platform access control and consent checks out of scope and permits a later full key search when `keyId` is absent. | No authenticated provider selection, protected authorization bound to the exact key and input, or durable same-operation result lookup. A nonextractable handle does not fill those gaps. |
| CSC API 2.2.0.0 `signatures/signHash` | `/info` lists supported `methods`, `asynchronousOperationMode` and `signAlgorithms`; `credentials/info` exposes credential `key/status`, `key/algo`, `SCAL` and `multisign`. CSC does not assign idempotent admission and lookup semantics to client-supplied `clientData`, or a distinct wire result for an uncertain outcome. [The separately pinned WebAuthn version 6 draft](https://raw.githubusercontent.com/yubicolabs/webauthn-sign-extension/7dcd66cb9a4a75c9f2a654ba90cfdbcf8e22e24f/index.bs) and the W3C pull request snapshot remain proposal sources, not deployment evidence.

The WebAuthn signing proposal already binds a selected signing key handle and exact `tbs` in the ceremony. CSC already defines credential, hash, authorization and asynchronous polling fields. This proposal does not duplicate those fields, change what their signature algorithms sign, or add a generic signed envelope, permit or receipt. Its only proposed CSC wire-level change is a negotiated meaning for existing `clientData` and a client-ID lookup form of existing polling, as specified in section 4. Other hosts may choose a different API shape but must meet the same behavior before claiming it.

For the algorithm-specific check, the pinned [CSC Data Model 1.0.0](https://cloudsignatureconsortium.org/wp-content/uploads/2025/10/csc-dm.pdf) section 7.6 defines `signAlgoParams` as base64-encoded DER when required. [RFC 8017](https://www.rfc-editor.org/rfc/rfc8017.html) Appendix A.2.3 defines RSA-PSS parameters and their defaults; [RFC 4055](https://www.rfc-editor.org/rfc/rfc4055.html) section 3.3 explains why a key algorithm OID alone cannot establish every RSA-PSS parameter restriction. Their exact source bytes are pinned in [sources.json](sources.json).

## 2. Conditional protected-operation contract

An implementation claims **protected authorization** only if the component controlling key invocation checks the authorization before invoking the key. It must bind the authorization to the actually selected provider or authenticator, key or credential, algorithm including parameters, input kind, exact input bytes or ordered digest bytes, authenticated requester scope, and one operation ID. The requester scope is WebAuthn RP ID and origin for a WebAuthn host, browser origin for a remote-key host, or authenticated service/client audience for CSC; it is not a fictitious universal origin field. For a CSC host, the service and requester identity used for this scope must come from the authenticated endpoint and caller context, separately from any client-supplied request field. An authorization for a digest does not prove that the signer saw or approved the digest's preimage.

The implementation must reject an unavailable selected key, changed algorithm or parameters, changed input, expired or revoked authorization, changed audience, and a same-ID/different-request collision before dispatch. It must not silently select another key or provider. If the host permits multiple eligible credentials, the verifier uses the *actual* selected credential ID and its matching key handle; a mere list of eligible keys is not an authorization for all of them. A logical credential ID or service URL alone is insufficient when it can be remapped: the key-invoking component must resolve and pin an immutable identity for the actual provider instance and key version or key material under that ID. If it cannot distinguish an alias remap, it cannot claim protected authorization for that selection. For prehashed algorithms, the hash algorithm and whether the bytes are a digest are part of the authorization. For message-signing algorithms, the exact message bytes are the input. A transport must preserve those bytes across asynchronous boundaries.

The enforcement component durably reserves the ID and the authorization's usable slot with an immutable comparison of all security-relevant request fields and the resolved provider/key identities before dispatch. At the key-invoking boundary it re-resolves or uses a pinned handle and compares the effective provider instance, key identity, algorithm and input to that reservation again; any mismatch fails without invocation, even if the credential ID or service URL is unchanged. It records dispatch before invoking an external signer. The slot remains spent through crashes, revocation, key-handle reallocation and account recovery. A completed outcome is immutable. An unresolved dispatch must remain unresolved until the original provider's outcome is established; a timeout or cancellation cannot prove non-execution. A same-ID retry or status query never invokes the key to recreate a missing response. If outcome retention ends, a spent-grant or ID tombstone must still prevent reuse for the lifetime of any replayable authorization. If the provider cannot guarantee these properties, it must not claim **same-operation recovery**.

The authenticated outcome must identify, or be verifiably linked to, the resolved provider/key identity as well as the selected credential, algorithm, input and operation ID. Existing WebAuthn assertion data or an authenticated service response may carry that link where the actual signer supplies it; an unsigned field appended by the application is not enforcement evidence. A raw signature alone cannot prove the protected authorization check. The caller must authenticate to query the outcome, and the service must scope query and cancellation-status access to the original requester. A repeated completion must pass the same outcome authentication and binding checks before the stored result is disclosed. Retention and expiry must be declared; after retention ends, the answer is unknown, never permission to replay under the old ID.

## 3. Capability declaration and evidence

Capability statements are separate claims, not an ordered ladder:

1. **Raw signing:** the API can sign with a selected key and algorithm.
2. **Ceremony evidence:** an authenticated WebAuthn assertion can show the ceremony's RP binding and UP/UV bits, and verified signing-key attestation can support its fixed policy. This does not assert document display or application-specific authorization.
3. **Protected authorization:** the actual key-invoking component enforces the bound authorization described in section 2.
4. **Same-operation recovery:** that component also implements the durable reservation, immutable result and client-known lookup described in section 2.
5. **Protected display or additional user verification:** claimed only with separate authenticated evidence of the actual displayed content or verification event.

A declaration names the implementation and exact supported scope, including algorithms, input kind, requester scope, retention and recovery behavior. The version 6 WebAuthn proposal's optional `support` request and `supportedAlgorithms` result report authenticator algorithm combinations; they do not declare this contract's protected authorization or recovery. For CSC, existing `/info` `methods` and `signAlgorithms` and credential `key/status`, `key/algo`, `SCAL` and `multisign` should inform the service's declared scope; a proposed profile needs an authenticated service policy for its narrower enforcement and recovery commitments. Retention behavior must identify the deadline's start event and enforce it across restart without extending it on retry or duplicate completion. If an asynchronous `validity_period` is omitted, the profile must admit a finite positive effective default from that authenticated policy or decline the protected-recovery claim; it must pin the effective period with the operation. A TLS-authenticated service statement can declare that policy, but neither the published fields nor the statement independently proves the service's internal enforcement. A stronger hardware or isolated-component claim needs verifiable evidence binding the implementation, admitted policy authority and update or rollback behavior. A caller must reject a stronger unsupported claim, not infer it from nonextractability, a generic `sign` result, an RP-generated receipt or a provider's self-description.

For a CSC credential, a current authoritative `key/status: disabled` means that key is unavailable for a new protected operation or a reserved operation not yet dispatched. The service must check the effective status again at the key-invoking boundary, even if an earlier capability declaration showed `enabled`. A change after dispatch does not establish non-execution or permit a same-ID retry to invoke another key; the original operation remains unresolved until its authenticated outcome is known.

Likewise, the current authoritative service capability state must support `signatures/signHash`, `signatures/signPolling`, asynchronous operation and the requested signature algorithm before this CSC profile admits or dispatches a new operation. For a parameterized request in this bounded profile, the effective service statement must also list the exact opaque `signAlgoParams` value in `signAlgorithms.algoParams`; an absent or different list does not establish support. CSC `/info` publishes `methods`, `asynchronousOperationMode` (omitted means synchronous only), `signAlgorithms.algos` and conditional `signAlgorithms.algoParams` for these checks. This list is not assumed to pair positionally with `algos`, nor does membership establish that an algorithm, its parameters and `hashAlgorithmOID` are mutually valid; the service must enforce that compatibility separately. A stale client discovery result or a separate profile assertion cannot override an effective service exclusion. A later loss of support must not turn a previously dispatched same-ID retry into a new invocation; recovery still reads the durable original state.

The one-operation reference model checks a deliberately explicit algorithm scope: RSA with no signature parameters and a declared SHA-256, SHA-384 or SHA-512 digest OID, or RSA-PSS with canonical Data Model base64 of DER parameters containing explicit supported hash and MGF1 identifiers. For RSA-PSS, the model derives the message hash from the parameters, rejects an explicit contradictory `hashAlgorithmOID`, and verifies the digest length. RFC 8017's omitted SHA-1 defaults and unknown algorithms fall outside this profile. The optional CSC `hashAlgorithmOID` may be absent when valid RSA-PSS parameters already imply the hash; a present JSON `null` is not absence and is rejected. CSC's input table says an implied hash makes that field unnecessary, while its error list identifies contradictions; this profile declines a contradictory supplied OID rather than treating it as an override. Parameter advertisement remains only a necessary service capability check.

For its selected-key fixture, the model additionally requires verified current credential evidence tied to the resolved provider and key identities at admission and key invocation. It uses the credential's reported key algorithm family and a certified public-key AlgorithmIdentifier. A generic `rsaEncryption` key with DER NULL parameters has no certificate-level PSS parameter restriction in this bounded check. A PSS-restricted key cannot be used for the parameter-free RSA fixture. A certified PSS key with parameters requires the requested PSS hash and MGF1 hash to match and its signature salt length to meet the certified minimum; absent certified PSS parameters impose no such field comparison. These are the RFC 4055 section 3.3 cases, not a universal equality check between `credentials/info.key/algo` and `signAlgo`. Unknown or unverified selected-key evidence declines the protected claim.

For RSA-PSS, the model also requires a current verified actual RSA modulus length in bits for that selected key, corresponding to CSC `credentials/info.key/len`. RFC 8017 uses `emLen = ceil((modBits - 1) / 8)` and requires `emLen >= hLen + sLen + 2`, where `hLen` is the PSS message-hash output length and `sLen` is the requested salt length. The model checks this necessary encoding capacity before reservation and again before invocation; an absent, non-integer, unsafe or insufficient length declines. It does not infer modulus length from the signing OID, service advertisement or digest bytes. A fitting capacity is not a security minimum, a provider-support promise or proof of key invocation. The parameter-free RSA fixture has no PSS capacity calculation. An actual service must verify the certificate, current key metadata, correspondence of reported `key/len` to the actual selected modulus, specific supported algorithm/parameter pair and signer enforcement; the synthetic `verified` flag does not perform those checks.

## 4. Minimal CSC profile example

This section is a **proposed opt-in profile**, not CSC 2.2.0.0 behavior. It illustrates the smallest semantic addition in an API that already has the other fields. The provider first declares this exact profile and retention policy through an authenticated service policy. For one `signatures/signHash` request with one hash and asynchronous `operationMode: "A"`, the client chooses a fresh, unpredictable `clientData` value of the form `sc1:` followed by unpadded base64url encoding of 16 random bytes. Under this profile, and only under it, the provider interprets that value as the operation ID. The existing server-generated `responseID` and ordinary `signPolling(requestID)` remain valid. A provider declaring this profile must keep server-generated `responseID` values outside the `sc1:` prefix, so the two polling ID forms are unambiguous.

This bounded example admits only user-specific service authorization with an owner independently resolved from the authenticated service token. It excludes non-user-specific service authorization; it does not let a client choose an owner by sending `userID`. The authenticated owner is part of the protected scope even when several users share the same service and client audience. This is an internal authorization condition, not a new CSC request field.

Before signing, the service durably binds that ID and its server-generated `responseID` to the authenticated client/audience and credential owner, selected service and `credentialID`, internally resolved provider instance and key identity, one authorized digest, `hashAlgorithmOID`, `signAlgo` and parameters, SAD or credential authorization reference, requested operation mode, admitted `validity_period` and `response_uri` (including their absence or effective defaults). These last two are existing CSC asynchronous controls: a retry must neither change outcome retention nor add or redirect a completion notification. An omitted `validity_period` uses a finite positive default declared by the authenticated profile policy; without one, this recovery profile does not admit the operation. Invalid explicit periods likewise cannot establish bounded recovery. The service pins the effective period at admission and uses it for completed-outcome expiry, regardless of a later policy change. The resolved identities are internal enforcement values, not new CSC request fields. It enforces the authorization against this exact tuple. Operation records and consumed authorization slots are scoped by the authenticated service and requester before an ID match, collision, status or spent-grant result is exposed. A request claiming a different service or audience is rejected before record lookup. For an authenticated caller outside the stored scope, a reused ID must not disclose whether another caller has an operation. Repeating `signatures/signHash` within the stored scope with the same ID and request fields returns the original status or `responseID` without reselecting a key or dispatching again, even if an alias has since changed; changing any bound request field rejects. A new admission or a reserved operation awaiting dispatch rejects a remap to another provider or key. The service must not rely on a digest of a JSON serialization whose normalization is unspecified: it compares the decoded typed values and exact digest bytes, including their order where an API supports more than one. The one-hash restriction here avoids defining batch partial-result semantics.

If the initial response is lost, a profile-aware client may call `signatures/signPolling` with the original `sc1:` `clientData` value **as the value of the required `requestID` field**, while supplying user-specific service authorization and omitting `userID`, to look up its own operation. The optional polling `clientData` field retains its ordinary application-data meaning. This is the sole proposed polling request extension: it lets the original requester look up its own operation and never submits another signing request. CSC 2.2.0.0 defines `requestID` only as the server-generated `responseID`, so an ordinary server may reject the profiled value with `invalid_request`; clients must not assume this extension without the authenticated profile declaration.

For this negotiated client-ID form only, a completed one-hash operation uses the existing HTTP 200 JSON `signatures` array of standard base64-encoded signature bytes in input-hash order; a durable reservation known not to have completed uses the existing HTTP 202 meaning with no response body. If the operation crossed the key-invocation boundary and may have completed but its outcome is unestablished, the proposed response is HTTP 200 JSON `{"outcomeState":"unresolved"}` without `signatures`. A durable pre-invocation stop with no signer call uses HTTP 200 JSON `{"outcomeState":"not-invoked"}`; this does not restore the spent authorization slot. HTTP 202 cannot represent the unresolved case, because CSC says 202 means processing has not yet completed. A successful HTTP 200 here confirms the *lookup*, not completion of the signing operation; only `signatures` is a completed signing outcome. These two `outcomeState` values are new profile semantics, not CSC 2.2.0.0 responses.

For this form, optional polling `clientData` remains application metadata independent of `requestID`; when supplied, it must be a string. An invalid type receives HTTP 400 `invalid_request` before any record result is read. A supplied `userID`, including explicit null, is rejected in this user-specific profile because the authenticated owner is implicit.

Unknown, expired, malformed or another authenticated requester's client ID all receive the identical opaque HTTP 400 JSON `{"error":"invalid_request"}` under this profile. It means no outcome is retrievable to that caller, never that the key was not used; no differing description may disclose another requester's operation. An unauthenticated caller receives HTTP 401 `{"error":"invalid_token"}` before ID lookup. These mappings use CSC's existing error vocabulary but add a profile-specific privacy rule; CSC does not define this unknown/expired equivalence. The server-generated `requestID` path keeps ordinary CSC behavior. The one-operation reference model tests only the proposed `sc1:` client-ID form, not all base polling responses or a deployed server. `clientData` has no idempotency guarantee outside this negotiated profile and must not be repurposed silently by an ordinary CSC client.

For completed outcomes, the synthetic model starts the admitted effective `validity_period` at the first authenticated completion and allows retrieval through that deadline. On the first later time advance it erases the result but retains the operation ID and spent authorization as a durable tombstone. A same-request retry then has unknown outcome status; a changed request under that ID still collides. Neither can restore the result or invoke the signer, even when the original authorization is still usable by time; a different ID cannot reuse its consumed slot. CSC defines `validity_period` as the maximum period for outcome availability, but does not supply this profile's client-ID lookup or choose its retention clock anchor. A deployed profile must declare and durably enforce its own clock rule and observable expiry treatment.

This example does not claim CSC SAD is always bound to one digest or one key. The profile is available only for an authorization mode in which the service can enforce the exact tuple and consume one usable signature slot. A broader SAD, an unscoped key search, a synchronous-only endpoint or a provider without durable reservation yields only the narrower supported capability. The same requirements could inform a future WebAuthn or Remote CryptoKeys amendment; no browser or authenticator behavior is asserted here.

## 5. Privacy, evaluation and open questions

Stable provider, key and operation identifiers can correlate activity. The client ID is random and scoped to one service and requester; outcome queries require authorization, disclosure is limited, and retention is bounded. A status query itself can reveal signing activity, so a profile must define rate limits and observable errors without confusing access denial with proof of non-execution.

[cases.json](cases.json) contains synthetic positive and negative transition vectors. Its fixed `clientData` value is for reproducibility; live clients must generate fresh unpredictable values. `baseSelection` and `baseAuthorizationSelection` model internal provider/key identities; `baseAuthenticatedCaller` and each vector's `callerPatch` model trusted service, client audience, user-specific authorization mode and independently authenticated owner supplied separately from `requestPatch`. The synthetic authorization owner is a trusted grant constraint, not a CSC wire field. A vector's `omitValidityPeriod` models absence of that optional CSC request field and its corresponding authorization-policy value; `defaultValidityPeriod` is a trusted profile-policy fixture, not a new CSC field. `baseCredentialStatus`, `initialCredentialStatus` and `changeCredentialStatus` model trusted current credential state separately from request data; `baseServiceInfo`, `serviceInfoPatch`, `changeServiceInfo` and `omitAsyncSupport` model current authoritative values corresponding to existing CSC `/info` fields. `baseSelectedKeyEvidence`, `selectedKeyPatch` and `changeSelectedKeyEvidence` model current trusted credential and certified-key restrictions separately from client request fields. Their `keyLenBits` stands for a verified actual RSA modulus length corresponding to selected-credential `key/len`; `verified` is an assumption for the synthetic run, not certificate or modulus validation. The internal `key-incompatible` state is not a CSC wire error. In this fixture, `BQA=` denotes DER NULL parameters for generic RSA, while `null` on a certified PSS key denotes absent AlgorithmIdentifier parameters. The `null` base request `signAlgoParams` is a separate synthetic no-parameter sentinel. These fixtures are not new CSC request or policy objects. `npm run check` replays the vectors against a one-operation reference model and validates the pinned source metadata. Most vector statuses describe model states, not CSC wire responses; the `poll` action alone tests proposed HTTP code and JSON body pairs for the `sc1:` client-ID form. A completion step's `signatureBytesHex` supplies fixed synthetic signature octets; the polling vectors check both canonical base64 and recovered bytes. `wireFixture` is a test-harness boundary for negotiated polling: a completed wire fixture requires validated octets, while older internal-only state vectors may retain symbolic markers. It is not a service capability or CSC wire field. `inspectDurable` is a test-only state projection used to confirm result erasure and spent-grant retention after expiry and restart. The separate `authenticated` flag on a completion step stands for verification of an outcome bound to the recorded request and resolved selection; it is not a cryptographic proof. The model's `advance` action represents a trusted clock; it does not test clock rollback or distributed storage. The model tests the proposed contract, not a deployed browser, authenticator, CSC server, or hardware enforcement. Open design work remains for an interoperable WebAuthn or remote-key API shape and independently verifiable enforcement evidence.

The RSA-PSS positive vectors use base64 DER encodings of SHA-256, SHA-384 and SHA-512, each with MGF1 using the same hash and a matching salt length; all three were independently decoded as ASN.1. Other valid SHA-256 DER values change only the salt length to exercise both service advertisement and the certified key's minimum. `omitHashAlgorithmOID` models the conditionally absent field on both request and authorization. The selected-key vectors cover matching and contradictory certified PSS parameters, a shorter and longer signature salt, insufficient 1024-bit capacity, the 1033/1034-bit encoding boundary, unknown or unsafe lengths, changes before or after dispatch, and same-ID recovery without re-invocation. Fourteen profile polling vectors cover the required requestID field, known-incomplete 202, uncertain completion, completed signatures, durable pre-dispatch stop, opaque unknown/expired/other-requester handling, and authentication before lookup. These vectors prove the reference model's defined checks, not a real certificate, the selected credential's cryptographic capability or an actual signature.
